### 成果物

`safe-store.js`（`window.SafeStore`）が3層の防御を担う。**本番へ書き込む関数は存在しない。**

| 層 | 実装 | 効果 |
|---|---|---|
| 第1層 | `guardCheck()` | 全消失・急減（既定60%未満）・読込前保存をブロック |
| 第2層 | `app/notebook_v2_snap` | 直近5世代を保持。起動時に1世代積む |
| 第3層 | `localStorage['awsStudyDeckV2Mirror']` | クラウド障害時の控え |

### v2ブランチのファイル構成

```
index-v2.html   ← 元 index.html。インラインFirebaseモジュールをブート処理に差し替え
app-v2.js       ← 元 app.js のコピー（段階3-1時点で中身は無変更）
data-v2.js      ← 元 data.js のコピー（段階3-1時点で中身は無変更）
safe-store.js   ← 新規。保存レイヤー
store.js        ← 共有。FIREBASE_CONFIG の供給元
```

設置済み。`michael-803.github.io/aws/index-v2.html` で動作確認済み。

### 調整ポイント

`safe-store.js` 冒頭の定数。

- `SYNC_MODE` … `'refresh'`（既定）/ `'keep'`（保存機能をテストするとき）
- `GUARD.dropRatio` … 既定 `0.6`
- `MAX_GENS` … 既定 5

### コンソール操作

```js

await SafeStore.listSnapshots() // 控えの一覧
await SafeStore.restore(0)      // 0番目の控えから復元（自動リロード）
```

## 4. 段階3の確定仕様

### 4-1. 安定ID化【最重要・最初にやる】

**問題**：組み込みカードのIDが `b::カテゴリ::配列index`、過去問が `QQ.indexOf(q)`、
模試が `examId:問題番号`。**どれも配列の並び順に依存**しており、1件でも挿入・削除・
並べ替えをすると、過去の学習履歴が別の項目にズレて付く。

**対応**：全413項目に明示IDを付与し、既存履歴を移行する。

| 対象 | 新ID | 現キー | 移行方法 |
|---|---|---|---|
| 組み込みカード151枚 | `B0001`〜`B0151` | `b::カテゴリ::index` | 現 `data.js` の並び順から機械生成（生成可能を検証済み） |
| 独自カード | `C<timestamp>`（現状維持） | `c::<timestamp>` | 変更不要。**既に安定** |
| 過去問67問 | `Q001`〜`Q067` | `String(index)` | 現 `data.js` の並び順から機械生成 |
| 模試195問 | `M1-001`〜`M3-065` | `examId:index` | 現 `mock-exam.html` の並び順から機械生成 |

**カテゴリにも安定IDを振る**（`cat_compute` 等）。現状は日本語文字列がキーなので、
将来カテゴリ名を変えると進捗・独自カードの所属が壊れる。`data.js` を触るこの機会に潰す。

### 4-3. 単語帳の機能追加

**タブ（カテゴリ）ごとの進捗保持**
現状 `fcTabState` は `datasetKey`（= `'aws'`）単位で1つだけ。これをカテゴリ単位に分割する。

```
fcProgress: {
  '<カテゴリID or __all__ or __weak__>': {
    orderIds: [], pos: 0, shuffled: false, reverse: false, answeredIds: []
  }
}
```

容量試算：全カテゴリ分で約8KB。Firestoreの1MiB上限に対して十分余裕あり。負荷の心配は不要。

**シャッフルのトグル化**

> ⚠️ **この仕様は2026-08-24に変更した（第29節）。** 以下は変更前の記録。
> 現在は「通過済みのカードは据え置き、これから出る残りだけを混ぜ、位置（pos）は動かさない」。

- 押す（OFF→ON）… 現在のデッキをランダム並べ替え、先頭へ
- もう一度押す（ON→OFF）… **シャッフル中に答えていないカードだけ**を、本来の並び順で出題
- さらに押す … 残り（未回答分）を再びランダム
- **一周して全部答えたら `answeredIds` を自動リセットし、全カードに戻る**（確定仕様）
- 「答えた」の定義 = 「わかる」「わからない」のどちらかを押した

**全カードに編集・削除ボタン**
組み込みカードは `data.js`（コード）にあるためアプリから消せない。よって：

- 編集 … 上書きレイヤー `cardEdits: { 'B0001': {term, def, img} }` を重ねる
- 削除 … `hiddenCards: ['B0001']` に入れて表示から除外する**論理削除**
- **「非表示にしたカード」一覧画面を用意し、いつでも復活できるようにする**

**改行対応**
`white-space: pre-wrap` を当てる。textareaの改行がそのまま表示される。
HTMLを解釈しないので安全（`escHtml` はそのまま維持）。

**画像対応**
Firebase Storageは**使用不可**。2026年2月3日以降、バケットの作成・維持にBlazeプラン
（クレジットカード登録）が必須。Sparkのままだと402/403エラーになる。
Firestoreへの直接埋め込みも1MiB上限のため不可。

→ **Cloudinaryを使う**（さくらさんの既存アカウント `dnbbwfwoi`／BreakinSetBuilderで使用実績あり）。
**アプリから直接アップロードする方式**（確定）。Firestoreには `secure_url` 文字列のみ保存するので、
カードが増えても容量は問題にならない。必要な設定は第6節を参照。

### 4-8b. 選択肢シャッフル機能【完了】

択一式・複数選択式の全問題で、選択肢の表示順を固定にしておくと「位置で答えを覚えてしまう」
という学習上の弱点が生まれる。これを避けるため、以下の仕様で選択肢シャッフルを実装した。

**対象**：複数選択問題（`MULTI_Q`）／過去問（`QQ`）／シナリオ問題（`SCENARIO_Q`）の3つ全て。

**仕様**：
- 設問を開く（描画する）たびに、選択肢の表示順をFisher-Yatesでシャッフルする
- 一度表示された後、その設問に解答するまでは表示順を固定する（再描画は次の設問に進むときにしか
  発生しない設計のため、自然と満たされる）
- **正誤判定・DOM要素ID・選択状態・誤答プールへの記録は、常に元データの配列インデックス
  （選択肢の内容そのものと1対1で対応する安定した識別子）を基準に行う。表示位置には一切依存しない。**
  シャッフルは「見た目の並び替え」のみで、内部ロジックは表示順シャッフル導入前とまったく同じ
  インデックスベースのまま変更していない。
- 組み込み問題の編集・削除ボタン（複数選択問題のみ実装）は設問ID単位で動作するため、選択肢の
  シャッフルとは無関係に常に正しい設問を指す。編集フォームも元データ（未シャッフルの順序）から
  直接読み込むため、シャッフル表示中に編集を開いても正しい選択肢に正しく反映される
  （実データで実際にテスト済み）。

**今後の指針**：新しく選択式の問題形式（択一・複数選択問わず）を追加する場合は、
**最初からこの仕様（開くたびにシャッフル・解答まで固定・判定は内容/IDベース）を組み込むこと。**
後から追加するとレンダリング部分の手戻りが発生するため、最初の設計段階で織り込んでおくのが望ましい。

### 14-2. 【重要】CLFに無かった新しい出題形式が2つある

公式ガイドの「Question types」に、CLF-C02には無かった形式が明記されている。
**既存エンジンは択一式・複数選択式にしか対応していないため、2つの出題エンジンを新規実装する必要がある。**

| 形式 | 仕様（公式ガイドの記述） | 既存対応 |
|---|---|---|
| 択一式（Multiple choice） | 正解1つ＋誤答3つ | ✅ `QQ` エンジン |
| 複数選択式（Multiple response） | **5つ以上の選択肢から2つ以上**を選ぶ。全部合っていないと得点にならない | ✅ `MULTI_Q` エンジン（※選択肢数を5以上に増やす必要あり） |
| **順序問題（Ordering）** | **3〜5個の選択肢を正しい順に並べる。**順序も含めて全て正しくないと得点にならない | ❌ **新規** |
| **マッチング問題（Matching）** | **3〜7個の設問と選択肢を対応付ける。**全ペア正解で初めて得点 | ❌ **新規** |

**新エンジンのUI方針（スマホ優先）**

ドラッグ＆ドロップはスマホで操作性が悪いため使わない。

- **順序問題**：選択肢をタップした順に 1→2→3… と番号が振られる方式。「やり直し」ボタンで解除。
  データ形式は `{id:'O001', c:カテゴリID, q:設問, o:[選択肢...], a:[正解の並び順のindex配列], e:解説}`
- **マッチング問題**：左に設問、右に選択肢。設問をタップ→対応する選択肢をタップ、で線がつながる方式。
  データ形式は `{id:'MT001', c:カテゴリID, q:設問, l:[左...], r:[右...], a:{左index:右index}, e:解説}`
- **どちらも 4-8b節の指針どおり、選択肢シャッフルを最初から組み込む。**
  順序問題は表示順をシャッフルし、正誤判定は元データのindexで行う。

### 14-3. 単語帳：カテゴリの複数選択【さくらさん要望・2026-08-16】

現状の単語帳はカテゴリを1つしか選べない（`currentKey` が単一値）。
これを**任意の複数カテゴリを組み合わせて出題できる**ようにする。

**キーの設計（既存データとの互換を保つ）**

`fcProgress` のキーを以下のとおり導出する。**1つだけ選んだ場合は現行キーとまったく同じになる**ため、
既存の学習進捗はそのまま引き継がれる。

| 選択状態 | `fcProgress` のキー | 互換性 |
|---|---|---|
| 0件（＝全カテゴリ） | `_all_` | 現行と同一 |
| 1件 | そのカテゴリID（例 `cat_bedrock`） | **現行と同一** |
| 2件以上 | `m:` ＋ ソート済みIDを `+` 連結（例 `m:cat_bedrock+cat_genai`） | 新規 |
| 苦手のみ | `_weak_` | 現行と同一（今回は排他のまま。組み合わせ対応は将来課題） |

IDをソートしてから連結するので、選ぶ順番が違っても同じキーになる（＝進捗が分裂しない）。

**肥大化対策**：9カテゴリなら組み合わせは最大511通り。全部保存すると `fcProgress` が膨らむため、
**`m:` で始まるキーは直近10件のLRUで保持し、超えた分は古いものから削除する。**
単一カテゴリ・`_all_`・`_weak_` は削除対象にしない。

**UI方針**：**チップは常にチェックボックスとして振る舞う**（モード切り替えは無い）。

- カテゴリチップをタップするたびに、そのカテゴリを出題対象に入れる／外す。組み合わせは自由で個数制限なし
- 「全カテゴリ」チップは選択をすべて解除するボタンとして働く
- Firestoreの予約語（`__x__` 形式）を避けるため、接頭辞は単一アンダースコアを維持する（4-1節の既知の罠）

> **一度モード切り替え式（「複数選択」トグルを押してからチップを選ぶ）で作ったが、廃止した。**
> トグルを押す必要があることに気づけず、チップを2つタップしても切り替わるだけなので
> 「複数選択が実装されていない」ように見えてしまったため。**先に何かを押させる設計にしない。**

**スマホでの折りたたみ**：カテゴリが9つあるとチップが6段・233pxを占め、カードと
「わかる／わからない」が画面外に押し出される。`@media(max-width:680px)` では
`📂 カテゴリ ＜選択中の内容＞ ▼` という見出しに畳み、タップで開く形にする（PCでは常に展開）。
畳んだ状態でも見出しに選択中のカテゴリ名と枚数が出るので、何を出題しているかは分かる。

**この機能は `_engine/engine.js` 側に実装する**ので、AIF以降の全資格で使える。
CLF（`/aws/app.js`）は据え置き方針のため反映しない。CLFにも欲しい場合は別途相談。

## 28. ユーザー作成資格

さくらさん自身がアプリ内で資格を作り、単語帳として使えるようにする機能。
`certs/index.html`（ハブ）の末尾に「自分で作った資格」の節と
「＋ 新しい資格を作る」ボタンが並ぶ。

### 28-1. 背景とアーキテクチャ上の分岐点【最重要】

**既存資格とは成り立ちが根本的に違う。**

| | 既存資格（CLF・IP・FE） | カスタム資格 |
|---|---|---|
| カテゴリ定義 | `data.js` の `FC_CATS_DEF`（コミット済み） | **Firestore** |
| カード | `data.js` の `SAMPLE`（コミット済み） | **Firestore** |
| 資格の定義 | `cert.js`（コミット済み） | **Firestore** |
| 編集・削除 | 静的データへの上書き層（`cardEdits`／`hiddenCards`） | **直接CRUD**（上書き層なし） |

GitHub Pagesは静的サイトなので、閲覧者がその場でファイルをコミットすることはできない。
そのためカスタム資格は cert.js・data.js を持たない「完全動的」な資格として扱う。
**既存資格の機能トグル・処方箋・安定ID・上書きレイヤーはカスタム資格に持ち込まない**
（さくらさんの指示。もともと動的データなので上書き層は不要）。

**分岐点：`engine.js` は読み込まれた瞬間に `SAMPLE` と `FC_CATS_DEF` を評価する**
（`const FC_CATS = Object.keys(SAMPLE)` と `CAT_NAME_TO_ID` の構築）。
そのため動的モードでは、

1. ページが先にFirestoreからメタ（資格名・説明・カテゴリ）を読む
2. `window.CERT` / `SAMPLE`（空）/ `FC_CATS_DEF`（Firestoreのカテゴリ）を組み立てる
3. **そのあとで** `safe-store.js` → `engine.js` → `boot.js` を動的に注入する

という順序を取り、「静的モードのふりをして」共通エンジンを動かしている。
**この順序を崩すとカテゴリが空のまま確定する。**

**`engine.js` 本体への変更は `rebuildCatMaps()` の追加1つだけ**（カテゴリ表を作り直す関数。
静的モードでは従来と同じ結果になるよう、読み込み直後に1回呼ぶだけ）。
`FC_CATS_DEF` は**再代入せず配列の中身を入れ替える**こと。エンジンが参照を保持しているため。

> 💡 **好都合だった発見**：`state.customCards`（独自カード）はもともと
> 「Firestoreに直接CRUDする動的カード」で、`cardEdits`／`hiddenCards` を通らない。
> `SAMPLE = {}` にすれば、**追加・編集・削除・カテゴリ移動が既存コードのまま動く。**
> 新規に書き直す必要はなかった（さくらさんの「新規に書き直さない」という指示どおり）。

### 28-5. 決めたこと（2026-08-24 さくらさん選択）

| 論点 | 決定 | 理由 |
|---|---|---|
| Firestore構造 | **資格1件＝1ドキュメント＋軽量索引** | 既存の分離方針と同型。事故が1資格に閉じる |
| エンジン統合 | **動的ページ側で先読みして注入**（engine.jsはほぼ無改造） | 既存3資格の読み込み経路に触れないので影響がゼロ |
| 資格ID | **`u-` プレフィクス強制＋予約リスト照合** | 名前空間が構造的に分かれ、将来の資格追加でも衝突しない |
| カテゴリ削除 | **カードは「未分類」へ退避** | カード枚数が変わらず、SafeStoreの急減ガードに触れない。誤操作でカードを失わない |

**IDの決め方**：資格名からスラッグを作り `u-` を付ける（「Eiken」→ `u-eiken`）。
日本語だけの名前は英字が拾えないので `u-cert-1` と自動採番し、ユーザーが手で直せる。
既存資格（`clf`・`itpass`・`fe`・`aif`）と準備中の資格（`saa`・`soa`・`ap`・`sap`・
`scs`・`sc`・`sa`・`dop`）、および末尾が `-dev`／`_snap` のIDは拒否する。

### 28-6. 保存レイヤーへの追加：`replaceFields`【地雷を1つ潰した】

`SafeStore.save()` の既定 `{merge:true}` は**入れ子のマップを深くマージする**。
そのため `customCards` からカテゴリのキーを消しても**クラウド側には古いキーが残り**、
索引の枚数と実際の枚数がズレる（カテゴリを消せる資格でだけ起きる問題）。

→ `save(data, {replaceFields:['customCards','fcProgress']})` を追加した。
指定したフィールドを `mergeFields` で丸ごと置き換える。
**引数を渡さなければ従来と完全に同じ動作**なので、既存資格の呼び出しは1行も変えていない。

## 29. 単語帳シャッフルの仕様変更【2026-08-24・全資格共通】

### 29-1. 何が起きていたか

さくらさんからの指摘：**「途中まで進めた単語帳でシャッフルを押すと、進捗が吹き飛んで
0枚目からのシャッフルになる」**。

原因は2つが重なっていた（旧 `toggleShuffle()`）。

1. **押すと必ず `pos = 0` に戻していた。** 未回答カードを先頭へ集める設計だったため、
   カウンタが「61/151」から「1/151」に戻り、進捗が消えたように見える
2. **「回答済み」の定義が「わかる／わからない」を押したカードだけだった。**
   めくって ←→ で読み進めていたぶんは未回答のままなので、
   結局デッキ全体が混ざり、実際に最初からやり直しになる

### 29-2. 新しい仕様（確定）

**押しても進捗（今いる位置）を失わない。**

| 対象 | 扱い |
|---|---|
| すでに通過したカード（`order` の `pos` より前） | **順番も位置もそのまま据え置く** |
| これから出るカード（`pos` 以降） | OFF→ON でシャッフル／ON→OFF で本来の順に戻す |
| これから出るぶんのうち回答済みのもの | 後ろへ回す（未回答を先に出す） |
| `pos`（現在位置） | **動かさない。** カウンタは 61/151 のように続きから進む |

- トースト表示も「残り91枚をシャッフルしました」と、対象の枚数が分かる形にした
- **例外：最後の1枚まで来てから押したとき**（残りが1枚以下）は一周した扱いにし、
  全カードを組み直して先頭から出題する。`answeredIds` もここでリセットする
- 「答えた」の定義は従来どおり「わかる／わからない」を押したカード
  （`markAnswered()`）。**通過済みかどうかは `pos` で判断する**ので、
  ←→ で読み進めただけのカードも進捗として扱われるようになった

### 29-3. 実装

`_engine/engine.js` の `toggleShuffle()` を書き換え、Fisher-Yatesを
`shuffled(arr)` として切り出した（既存の `shuffleIndices(n)` とは別物。
あちらは選択肢シャッフル用）。**全資格共通のエンジンなので、
CLF-C02・ITパスポート・FE・カスタム資格すべてに同時に効く。**
保存形式（`fcProgress`）は変更していないため、既存の学習進捗はそのまま引き継がれる。

### 30-3. 【重要】data.js のグローバルは `window` に載らない

実装中に検証ハーネスが捕まえた不具合。

→ **バンクの実体はページ側から明示的に渡す**方式にした。

```html
<script src="../_engine/mock.js?v=1"></script>
<script>MockBoot({QQ:QQ, SCENARIO_Q:SCENARIO_Q, PSEUDO_Q:PSEUDO_Q});</script>
```

識別子が見えるのは `data.js` と同じスクリプト階層にいるページだけなので、
ここで渡すしかない。**新しい資格の模試を作るときも、この1行を忘れないこと。**
（`cert.js` の `pools:['QQ',...]` は「どのバンクを使うか」の指定で、

### 35-2. 裏（意味・説明）が長いときスクロールできるようにした

**原因はCSSグリッドの `1fr`。** `.study-face` は
`grid-template-rows:auto 1fr auto` で本文を中央の行に置いていたが、
**`1fr` は `minmax(auto, 1fr)` と同じで、最小サイズが min-content になる。**
そのため本文が長いとその行自体が伸びてカードからはみ出し、
本文に付けてあった `max-height:100%` と `overflow-y:auto` が効かなかった。

→ **`grid-template-rows:auto minmax(0,1fr) auto`** に変更（`min-height:0` も併記）。
これで行が縮み、本文側でスクロールが発生する。表（用語）にも同じ指定が効く。

**スクロールバーは細く整えた**（`scrollbar-width:thin` と
`::-webkit-scrollbar` 系）。単語カードのほか、出題エリア・カテゴリ編集・
擬似言語コード・モーダルにも同じ見た目を適用している。

**スクロールバーをつまんでもカードがめくれないようにした。** カードは
クリックでめくれる作りなので、スクロールバーをクリックすると同時にめくれてしまう。
`fcFlip(event)` にして、**本文がはみ出していて、かつクリック位置が
要素の表示幅より右（＝スクロールバーの領域）のときだけ無視する**ようにした。
本文そのもののクリック・キーボードの Space は従来どおりめくれる。

> 💡 **グリッドやフレックスの中で `overflow` が効かないときは、
> まず `minmax(0,1fr)` と `min-height:0` を疑うこと。** 最小サイズが
> min-content のままだと、いくら子要素に `overflow` を書いても縮まない。

### 43-2. 【新規実装】長文設問モード（全資格共通・影響ゼロで入れた）

第11節 ※2 に「SAPは1問が数百字。既存のシナリオUIでは表示が破綻するため
長文モードの新規実装が必要」と申し送りがあった。今回それを入れた。

**やったこと**

- `_engine/engine.js` に `qStem(q)` と `isLongStem(text)` を追加。
  設問文がしきい値以上なら `<div class="quiz-question long">` を出す（エンジンの既定は130字）
- 設問文を描いていた**6箇所**（engine.js 3・engine-formats.js 2・engine-pseudo.js 1）を
  すべて `qStem(q)` 経由に統一。模試側（mock.js）も2箇所で同じ判定にした
- `.quiz-question.long` は 15px・通常の太さ・行間1.95・`white-space:pre-wrap`・左に罫線。
  既定の `.quiz-question` は16px太字なので、長文をそのまま流すと読み通せない
- しきい値は `CERT.longStem` で資格ごとに上書きできる（SAPは130を明示）

**既存資格への影響はゼロ。** しきい値130字は、既存6資格の設問の最長（CLF-C02の117字）より
上に取ってある。全資格の全設問を数えて確認済み。

|---|---:|---:|
| CLF-C02 | 117字 | 0問 |
| ITパスポート | 79字 | 0問 |
| 基本情報 | 107字 | 0問 |
| 応用情報 | 97字 | 0問 |
| SAA-C03 | 96字 | 0問 |
| SOA-C03 | 76字 | 0問 |

> 💡 **共通エンジンに手を入れるときは、しきい値を「既存の最大値より上」に取れば
> 影響ゼロで新機能を入れられる。** 機能トグルを増やす前に、この形で済むか考えること。

#### 【訂正】SAPのしきい値は130字ではなく90字（2026-08-27・第2チャンクで判明）

第1チャンクの時点では、しきい値を130字とした根拠が
「既存資格の最長（CLF 117字）より上だから」という**既存への影響だけ**だった。
肝心の「SAPの設問がその長さになるのか」を実測していなかった。

第2チャンクで長文シナリオを40問書いて数えたところ、**130字を超えたのは1問だけ**だった。

| | 最短 | 中央 | 最長 |
|---|---:|---:|---:|
| SAPの四択 | — | — | **66字** |
| SAPのシナリオ | **96字** | 112字 | 170字 |

日本語は英語より字数が短くなるため、130字という数字は英語の問題文の感覚に
引きずられていた。四択（最長66字）とシナリオ（最短96字）ははっきり分かれているので、
その間の **90字** を `CERT.longStem` に設定した。
これでシナリオ40問すべてが長文体裁になり、四択は1問も変わらない。

> ⚠️ **しきい値を決めるときは、必ず「実際のデータを数えてから」にすること。**
> 影響を受けない側（既存資格）だけを見て決めると、
> 効かせたい側（新資格）で機能しないものができあがる。
> 検証にも「シナリオは全問が長文体裁になる／四択は1問もならない」を
> 常設項目として入れた（`verify-mock.js`）。

> ⚠️ **なお、この40問（中央112字）は本番のSAPより短い。**
> 本番は状況の説明だけで200字を超えることも珍しくない。
> 第3チャンク以降は **150〜250字** を目安に書くこと。

あわせて `app.css?v=12`／`engine.js?v=11`／`mock.js?v=2`／`mock.css?v=2` に版数を上げた
（全13ファイル）。**古いタブは閉じて開き直すこと**（第7節の教訓）。

### 43-3. 【設計判断】単語帳は「設計パターン帳」にした

第11節 ※1 の方針どおり、SAPの単語帳は用語帳にしない。

| | アソシエイトまで | SAP |
|---|---|---|
| 表（term） | サービス名・用語 | **要件・状況**（「〜したい」「〜が起きている」） |
| 裏（def） | その説明 | **採るべき構成と、なぜ他ではないか** |

例：表「RTO数時間・RPO数時間で費用は抑えたい」→
裏「パイロットライト。データだけ継続複製し計算資源は停止または最小で置く。
バックアップ＆リストアはRTOが長い。ウォームスタンバイは常時費用が上がる」。

**本番で問われるのは知識の有無ではなく、要件から構成を選べるかどうか。**
裏に必ず「なぜ他ではないか」を入れるのは、そのまま消去法の練習になるため。

カテゴリは設計テーマ別の10個（マルチアカウント・組織統制／大規模ネットワーク設計／
移行の設計／データの設計／回復性・災害対策／セキュリティ設計／コスト最適化／
運用・自動化の設計／近代化・疎結合／ハイブリッド構成）。
**問題は公式の4ドメイン**で分類する（SAA・SOAと同じ方針・第40-2節）。

### 43-6. 第1チャンクで踏んだ落とし穴

**ルール6（正解だけが長い）が40問中9問。過去最悪の割合だった。**
原因は§40-7・§41-5とまったく同じで、正解にだけサービス名をフルで書いてしまうこと
（`'Discovery Serviceで構成と通信を収集する'` 28文字 対 誤答14文字）。

SAPは「構成を答える」試験なので、正解が説明的になりやすい。
**問題文の文脈で分かる固有名詞は正解側から落とし、解説側にフルネームを残す。**
`'依存関係を収集する'` に直しても、解説で Application Discovery Service に触れていれば
学習上の情報は失われない。

もう1つ、**難易度が「中」に68%まで偏った。** これも毎回同じ。
用語の対応を問うだけの問題（PrivateLink・Intelligent-Tiering・Fargateなど）は
迷わず「易」にしてよい。

### 43-7. 長文シナリオの書き方（第2チャンクで決めた型）

**「状況 → 制約 → 問い」の3段で書く。**

1. **状況**：何が動いていて、いま何が起きているか（アカウント数・VPC数・
   データ量・利用者数など、判断に効く数値を必ず入れる）
2. **制約**：予算・期限・停止時間・法令・改修できる範囲。
   **ここが選択肢を1つに絞る鍵になる。**制約が無いと複数の選択肢が正解になってしまう
3. **問い**：「最も適した◯◯はどれですか？」

例（`S038`）：「基幹システムをAWSへ移す。切替当日の停止時間は30分以内という制約があり、
問題が起きた場合は当日中にオンプレミスへ戻す必要がある。データ量は数TBで、
日々更新され続けている。最も適した進め方はどれですか？」
——**30分**と**当日中に戻す**と**数TB**の3つがそろって初めて、
「継続レプリケーションで並行稼働」以外が消える。

誤答は「一般論としては正しいが、この制約では成り立たない手」を並べる。
一括コピーも週末コピーも移行手段としては実在するが、30分と数TBの前では消える。

### 43-8. 第3チャンクで再発した指摘

**ルール6（正解だけが長い）が6問。** SAPでは3チャンク連続で出ている。
この資格は「構成を答える」ため正解が説明的になりやすく、
`'Application Migration Serviceで継続レプリケーションする'` 42文字 対 誤答20文字
のような形が繰り返し生まれる。

処置は毎回同じ（§40-7・§41-5・§43-6）。**固有名詞を正解側から落として解説に残す。**
`'継続レプリケーションで同期する'` に直し、解説の冒頭に
「Application Migration Serviceなら…」と書けば情報は失われない。

**ルール1（図つき20%）も再び割った**（17.9%）。第4チャンクの応用情報と同じ原因で、
分母が65問増えたのに図つきを比例して足していなかった。
4問を図参照の形に作り替えて20.7%へ戻した。

> 💡 **問題を N 問足すときは、同時に 0.2N 問の図つきを確保する。**
> 後から辻褄を合わせるより、書き始める前に図つきの割り当てを決めるほうが早い。
